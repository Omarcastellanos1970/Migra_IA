6. DATA LEAKAGE AUDIT
--------------------------------------------------------------------------
  [EXCLUDED] commercial_life_years
      identity verified in 9 of 9 rows: commercial_life_years =
      year(end_of_manufacturing) - release. The date it is derived from is
      one of the dates that define the label, so the column is the label
      written another way.
  [EXCLUDED] total_support_years
      identity verified in 6 of 6 rows: total_support_years =
      year(end_of_spare_parts) - release. The date it is derived from is
      one of the dates that define the label, so the column is the label
      written another way.
  [EXCLUDED] end_of_life_announcement / end_of_manufacturing / end_of_spare_parts
      they are the columns from which the class is derived. Using them as
      a variable would be predicting the label with the label.
  [EXCLUDED] level
      it measures how well verified the datum is against the source
      (A/B/C), not a property of the equipment. It is metadata of the
      collection process: if it got in, the model would learn the
      documentary habit of the manufacturer.
  [EXCLUDED as a variable] manufacturer
      it is the grouping variable. In leave-one-manufacturer-out the test
      brand never appears in training, so as a variable it is unusable: it
      only serves to form the folds.
  [ADMITTED] release -> age
      it predates any end-of-life event and it is available on the
      nameplate of the equipment. The only variable that survives the
      audit.

  RESULT: of the available columns, 1 survives.
  The set admits exactly one uncontaminated variable. That is the finding,
  and it conditions everything above: the classic model had no choice but
  to be univariate.

7. P2 REPLACEMENT PRIORITY - NOT EVALUABLE YET
--------------------------------------------------------------------------
  The classic model assigned to P2 is gradient boosting in ranking mode. It is
  not run, and the reason is not technical but one of data: a ranking model
  needs a reference ordering -which platform must be replaced before which-
  and that ordering does not exist in any source of the project.

  Deriving it from the score of the engine itself would be circular: the
  model would learn to reproduce the formula it is meant to evaluate.

  What is needed to unblock it, in order of cost:
     1. A priority ordering by expert judgement over these 9 platforms,
        issued by the co-authors without seeing the output of the engine. It
        is the same procedure as _blind_template.py and it can be asked for
        in one session.
     2. Enlarging the life-cycle table to the 130 generations of the
        catalog, which is what would give a set where boosting makes sense.
        Extraction and verification work on official sources.
